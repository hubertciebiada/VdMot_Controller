# Port notes

C++ behaviour that the Rust port keeps although it looks odd, C++ bugs found while porting, and
the places where a C++ test has no Rust form. One entry per finding: module, what, why it
matters. The rules are in [PORTING.md](PORTING.md).

## Kept quirks

| Module | What | Why it matters |
|---|---|---|
| common | `roundTargetPercent(0.49999999999999994)` returns 1: `v + 0.5` rounds to 1.0 in double precision before the truncation. | A target payload just below x.5 can round up. Kept for parity (`round_target_percent`, test `round_target_percent_cases`). |
| common | `isSafeName`/`isHostName` compute `maxLen + 1` in `size_t`; `maxLen = SIZE_MAX` wraps to 0 and accepts only "" (and only with `allowEmpty`). | None in practice (the limits are constants); kept with `wrapping_add`. |
| json_writer | A failed call rolls the text back but not the state flags its `beforeValue()` set (root written, key consumed, first element). | Not observable: the writer is poisoned until `reset()`, which clears them. Kept. |
| json_writer | `number()` formats with `printf("%.*f")`: glibc in the host tests rounds the exact binary value half to even and prints the sign of -0 ("-0.00"); the device runs newlib. | Rust implements the glibc rule with integers (`format_f64_fixed`), byte-identical with glibc on 255,169 random values (all exponents, near-ties, 0..18 decimals). Not compared with newlib on the device: a difference there would be a C++ host/device difference too. |
| version | `VDM_VERSION`/`VDM_MIN_STM_VERSION` are C++ build flags; Rust reads them with `option_env!` at compile time ("0.0.0-native" and "1.4.0" when unset). | The firmware build must export both variables, or the image reports "0.0.0-native". |
| line_assembler | `StaticLineAssembler<N>` requires N >= 2, the base class takes any capacity (0, 1 and null storage drop every line as overflow). | `LineAssembler<N>` owns its storage and allows N = 0 and 1 with the C++ base-class behaviour (the C++ null-storage case is N = 0). |
| lease_client | A lease config value the codec refuses (timeout 1..4 or above 1440 min, failsafe percent 101..254) makes `next()` return true with the empty `RequestLine{}` its failed `buildSetLeaseTimeout`/`buildSetFailsafe` left: the link refuses it (Invalid), the request is lost after 10 s and every round fails with reason 1 (`lease_config_failed` after 3). | Not reachable in the firmware: `effectiveLeaseConfig` reads a Config whose `timeoutMin` and `failsafePct` passed their OffOrRange/PctHold checks. Kept: `next()` gives `Some(RequestLine::default())` (test `a_config_value_the_codec_refuses_hands_out_the_empty_request`). |
| lease_client | `onCompletion` of a push answered Ok clears `pushMask_ & ~(1u << req.valve)`; for the empty request above (valve `kNoValve` = 254, only if a caller completed a request it never queued) the shift is undefined behaviour in C++ (x86: no bit of the 12-bit mask). | Rust clears no bit (`checked_shl`), the x86 result. Not reachable through the session. |
| calib_schedule | `calibSlotEpoch` checks only `ref.valid`: the date fields of the reference are used unchecked (the civil-date arithmetic gives some number for month 0 or day 255), and `ref.epoch + days * 86400 + secs` is signed 64-bit arithmetic that overflows (undefined behaviour) for an epoch within about 2^44 of the i64 limits. | The glue passes the `localtime_r` result of the epoch it hands in, so neither occurs. Rust gives the same numbers for unchecked fields (C++ truncating division kept) and wraps the final sum instead of panicking; equal to the C++ on 2 M random references with \|epoch\| < 2^62. |
| calib_schedule | `nextSlot` looks up to 7 days ahead without the year limit of the slot keys: from 9999-12-25 on it can return a key of the year 10000 (e.g. 100000101), which `restoreLastSlot` would reject. | None before the year 9999; kept. |
| web_guard | A Host (also the host of an Origin) of digits and dots only is taken for an IPv4 address and refused when it does not parse as one: a host name of digits only (the host name of a station named "1234") and a `web.allowedHosts` entry of digits only never match, although the config accepts both (`isHostName`). | Such a device answers 403 `host_not_allowed` under its own name and is reached by its IP. Kept for parity (`host_allowed`). |
| web_guard | `guardDetail` echoes at most 48 bytes of the Host or Origin and stops at a NUL in them (`printf("%.*s")`). | Not reachable through esp_http_server (header values are C strings). Kept (`guard_detail`, test `guard_detail_echo_ends_at_a_nul_like_printf_precision`). |
| mqtt_topics | `formatVolt` turns the first '.' into ',' with `strchr(out, '.')` also when `putf` wrote nothing: with capacity 0 and `germanComma` it scans, and may change, memory the caller did not hand over. | A C++ bug that cannot happen in the firmware (the MQTT client formats into 24 bytes). Rust changes only the text it wrote. |
| mqtt_topics | Rust differs: `formatVolt` prints `%.3f` through `format_f64_fixed`, which is exact below 2^128 only. For \|v\| >= 2^128 (39 digits and more) Rust returns 0 where the C++ prints the number into an output of 44 bytes or more. | Not reachable: volt values are (vad / 100 + offset) x factor with \|offset\|, \|factor\| <= 1000 (below 2.2e10), formatted into 24 bytes, where both return 0 from 1e19 on. The differential check of the three MQTT/target modules (512,048 cases) found 761 differences, all of this kind, and no other. |
| mqtt_policy | `ButtonGate::confirm()` and `expire()` take the held action in the lowest slot; the header says "the oldest held action of that topic", which a reused slot breaks (hold A, hold B, confirm, hold C: the next confirm gives C before B). | Not observable: the actions held for one topic are the same button. Kept (test `button_gate_confirm_takes_the_lowest_slot_also_after_a_slot_was_reused`). |

## Intended deviations

| Module | What | Why it matters |
|---|---|---|
| stm_flasher | Decision D9 (GLUE-DESIGN-STM.md §8): an image above 16 KiB is flashed in two passes of Erasing, Writing and Verifying, sectors 1..n first (blocks from 0x08004000 upwards), then sector 0 (blocks 1..63, block 0 last). C++ erases all sectors with one frame, writes blocks 1..n-1 and block 0, then reads back blocks 0..n-1. Each pass compares the CRC32 of the image bytes it verified with the CRC the Validating phase found for them (C++: one CRC of the whole image after the verify); a session retry repeats the current pass, and each pass has the `session_retries` of its own; an erase failure reports the first address of the erased range (0x08004000 for sectors 1..n, C++ always 0x08000000). The phases Erasing, Writing and Verifying (legacy codes 3, 4, 5) appear twice; `bytes_done` counts over both passes, and the percent holds at the value of the first verify during the erase and the writing of sector 0 (88 % for a 53,760-byte image) until the second verify passes it. Images of at most 16 KiB are flashed exactly as in C++. | Sector 0 keeps the old vector table and boot stage until the rest of the new image is written and verified: an interrupted flash (ESP crash, power loss) leaves the STM without a bootable vector table only during the sector-0 pass (about 2 s) instead of during the erase and write of the whole image. An old image whose boot stage lies in sector 0 (the Rust STM images) still answers the handshake after an interruption in the first pass, so the ESP can flash again. Pinned by `stm_flasher/tests_d9.rs`. |
| stm_flasher | Rust only (F4 of REVIEW-ESP-SAFETY.md): the sector-0 pass of D9 writes and verifies the image bytes of sector 0 from RAM (`FlashImage::hold_low`, 16 KiB). Before every erase of sector 0 they are checked against the CRC the Validating phase found for them and read from the image again when they are missing or differ; when that fails, the erase is not sent (`image_read` in Erasing). Once the sector list of that erase went out (`FlashStatus::sector0_at_risk`, until sector 0 verifies) a failure does not pulse NRST: the phase `Sector0Pending` (13, "sector0_pending", legacy status 8, active) keeps the ROM session, a new round of the pass (erase, write, verify, with its own session retries) starts every `sector0_retry_ms` (30 s) and at once on `retry_sector0`, and an abort is ignored. The verify of sector 0 clears the error of an earlier round. C++ pulses NRST after every failure that touched the STM. Images of at most 16 KiB keep the C++ behaviour. | The boards do not wire BOOT0, and an STM32F4 whose sector 0 is erased never reaches its ROM bootloader again: the reset after a failed sector-0 pass needed BOOT0 or SWD. Now only a power loss, an ESP restart or an ESP crash during the pass does (the restart rules: GLUE-DESIGN-ESP.md §4.7 row 12). A bootloader that lost a byte of a frame stays out of step with the 2-byte commands of the rounds; there is no resync step (the ROM protocol is unchanged). Pinned by `stm_flasher/tests_d9.rs`. |
| ota/update | `end()` never selects a slot that the update did not write completely: an update that leaves no image of its own (nothing written, or a last sector that failed and aborted it: a file of at most 4 KiB with a wrong magic byte, a failed flash write) ends with `UPDATE_ERROR_READ` ("Flash Read Failed", event 107 arg1 3) and no `set_boot`. C++ (Arduino-ESP32 2.0.7 `Update`): `end(true)` ignored the result of the last partial sector, wrote the stashed first bytes of the last image back and selected the slot: "Flash Read Failed" when no image had passed the magic check since boot, "MD5 Check Failed" when an MD5 was given, otherwise the slot booted when its image verified, with `end()` true and the failed sector's code still set, or "Could Not Activate The Firmware" (9) when it did not. | The operator's safety goal: an upload that fails never changes the boot image. In C++ an image left complete by an earlier upload of the same boot that failed its MD5 check became the boot image after a small wrong file. The codes change only where C++ selected the slot (now 3) or failed its activation (9, now 3). The C++ firmware keeps the bug until its own fix. Pinned by `ota/update/tests.rs` (`a_failed_last_sector_never_selects_what_an_earlier_update_left_in_the_slot`, `after_a_failed_first_flash_write_a_tiny_update_selects_nothing`, `an_update_that_wrote_nothing_selects_nothing`). |
| json_api | Decision 7.6 of GLUE-DESIGN-ESP.md: the router has `POST /api/system/ota/switch-back` (`ApiRoute::OtaSwitchBack`, number 45 after the C++ routes; the other methods get 405), where the C++ router answers 404. The body and the answers (`{"confirm":"switch-back"}`, 202, 400 `confirm_required`, 409 `busy`/`restarting`/`no_fallback`) are the glue's; event 109 reason 7 and event 107 arg1 -4 of the same decision are event_log's. | The manual switch back of the boot guard (GLUE-DESIGN-ESP.md §6.3) is the remedy for a confirmed image that misbehaves while its HTTP server works. Pinned by `json_api/tests.rs` (`route_of_the_ota_switch_back`). |
| app (RTC block) | The RTC block of a Rust image holds the boot guard's mirror first and the C++ records after it, at other offsets (`app::RTC_*`, GLUE-DESIGN-ESP.md 6.1); the record formats are the C++ ones. An OTA or a switch between the C++ and the Rust firmware loses every RTC record: each fails its check and counts as power-on garbage. Lost are the desired targets (the next image restores the NVS copy, which the restart path writes before every restart but which a switch of the boot guard at boot skips: it can be up to 30 min old, `TargetSaver::MAX_DELAY_MS`), the ESP lease emulation, the restart count of the network watchdog (VNWD) and the HA status (Unknown, as after a power-on). | Design decision of 6.1: the guard's mirror must come first. Within one firmware the records survive every software, panic and watchdog reset as before. |
