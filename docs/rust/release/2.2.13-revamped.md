## Highlights

Changes since 2.2.7, the last published release. The full list is at the end of these notes.

- **Valve control in l/min.** A valve with a measured flow curve takes its target as a flow, in
  steps of 0.1 l/min, limited by `qmax`. Each loop has its own curve of 2 to 16 points: pulses from
  the closed end stop against l/min.
- **Percent means the whole stroke.** With the flow layer running, a target of t % is t % of the
  stroke of the actuator: 0 % is closed, 100 % the open end stop. The API, MQTT and Home Assistant
  all use this scale for such a valve.
- **A new target does not go to the end stop.** A held valve reaches a new target with one service
  move. The end stop stays for closing, the first opening from 0 %, 100 %, an unknown position, a
  lost hold and a changed curve.
- **A failed positioning waits longer.** It is tried again after 5, 10 and 20 minutes, then every
  60 minutes, so the actuator does not run to its end stop every 5 minutes without end. A new target
  goes out at once. Event 417 and the `problem` flag on MQTT work as before.
- **The flow layer is optional and off by default.** A valve without it behaves as in 2.2.7.
  Measuring a curve, uploading it and enabling the layer:
  [INSTALL.md section 7](../INSTALL.md#7-the-flow-layer).
- **New dashboard views.** Valves is one row per valve, and a row opens to its actions, diagnostics
  and the chart of its flow curve. The new tab Stored is read only and shows what is stored and in
  which place: flow curves, calibration and failsafe, sensors, STM parameters, images.
- **MQTT and Home Assistant.** `valves/<V>/flow/set` takes the target in l/min, and Home Assistant
  gets the number entity `valves_flowTarget_<R>`, from 0 to `qmax` in steps of 0.1. The read topic
  `valves/<V>/flow` reports the flow, with sensors in Home Assistant.
- **More exact service moves.** A service move ends with a plug brake, on by default after an STM
  start. In a reference measurement on two controllers a further opening move missed a median of
  3 pulses instead of 28 to 60.
- **Boot fix.** The stack of `main` is 40 960 B. The 2.2.11 build overflowed the old 32 768 B before
  the logger and restarted until the boot guard switched back. No published release is affected.
- **STM32.** The code is that of 2.2.9. Coming from 2.2.7 or older, flash it: the flow layer needs
  STM 2.2.8 and the brake needs STM 2.2.9. Coming from 2.2.9 or newer, the flash only keeps the
  versions of the two MCUs equal.

## Known limits

- **The flow is calculated, not measured.** The firmware has no flow sensor and knows no drift of
  the flow over time. The l/min it shows comes from the curve at the held position.
- **Curves belong to one installation.** The reference curves were measured on cold water. Measure
  the curves of your own loops with a rotameter on each loop.
- **One reference installation.** The reference measurement covers one installation with 13 loops
  on two controllers.
- **Hardware coverage.** Only the image `STM32F411_C2` ran on hardware. The other three STM32 images
  pass Renode.
- **2.2.13 has not run on a device yet.** It passed the host tests, Renode and QEMU. Its flow layer
  ran on hardware as 2.2.12 with the circulation pump off, so operation while heating, with the pump
  running, is not confirmed. An ESP32 image that fails its trial returns to the previous one by
  itself.
- **NC valve inserts only.** The motion rules of 2.2.2 to 2.2.5 were derived on normally closed
  inserts. Nobody tested normally open inserts.
